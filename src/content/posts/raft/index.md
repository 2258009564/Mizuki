# 什么是Raft
Raft是一个分布式一致性算法，主要用于解决分布式系统中节点之间的一致性问题。它通过选举领导者、日志复制和状态机应用等机制，确保在分布式环境下的数据一致性和可靠性。

为了易于理解，Raft将共识算法分解为三个主要子问题：
领导者选举、日志复制和安全性。通过解决这三个子问题，Raft能够在分布式系统中实现一致性和容错性。

接下来，我将详细介绍Raft的工作原理和关键概念。
 
# 为什么需要 Raft
我们知道，客户端需要通过访问数据库来获取数据，执行操作。

在单点数据库中，客户端的请求可以直接发送到数据库，数据库处理请求并返回结果。

然而，在实际生产环境中，单点数据库存在故障风险，可能导致数据丢失和服务中断。为了提高系统的可靠性和可用性，我们考虑将数据库部署在多个机器节点上，形成一个分布式数据库集群。

显然的，分布式架构比起单点架构具有以下优势：
1. 高可用性：即使部分节点发生故障，整个系统仍能继续运行。
2. 可扩展性：可以通过增加节点来提升系统的处理能力和存储容量。
3. 数据冗余：数据在多个节点上进行备份，提高了数据的安全性和可靠性。

我们最终期望这个 分布式集群 可以像单点数据库一样对外提供服务，客户端只需通过固定的入口访问集群即可获得数据和执行操作，而无需关心集群内部的节点状态和数据分布。

但实际上，集群中的节点可能因为各种原因发生故障，譬如**网络分区**导致节点之间无法通信，或者某些节点**宕机**无法提供服务。这种情况下，客户端的请求可能会被发送到不同的节点，而这些节点可能拥有**不同的数据状态**。这对于客户端来说是不可接受的，因为它们期望从集群中获取一致的数据结果。

Raft的目标就是解决这个问题，确保在分布式集群中，所有节点能够达成一致的状态，从而为客户端提供一致的数据访问体验。

我们不妨将问题抽象：现在有两台数据不相同的设备，我们最终希望它们的数据状态保持一致。我们当然可以通过完全覆盖的方式实现一致性：把好设备A的数据完全覆盖到坏设备B上。

这种操作意味着我们需要将整个数据集从A传输到B，这在数据量大时会非常耗时和低效。

因此，Raft 引入了**复制状态机**的概念。

# 复制状态机
复制状态机的概念：相同的初始状态  => 相同的输入序列  => 相同的最终状态

在Raft中，leader 将 客户端请求(command) 封装到一个个 log entry 中，将这些 log entries 复制到所有 follower 节点，然后大家按相同顺序应用 logentries 中的 command ，根据复制状态机的理论，大家的结束状态肯定是一致的。

可以说，我们使用共识算法，就是为了实现复制状态机。一个分布式场景下的各节点间，就是通过共识算法来保证命令序列的一致，从而始终保持它们的状态一致，从而实现高可用的。---什么是高可用

这里稍微拓展一点，复制状态机的功能可以更加强大。比如两个副本一个采用行存储的数据结构存储数据，另一个采用列存储，只要它们初始数据相同，并持续发给他们相同的命令，那么同一时刻从两个副本中读取到的结果也是一样的，这就是一种HTAP的实现方法(比如TiDB) ---这里我还没懂 行存储和列存储之类的

# 状态简化
在 Raft 中，节点的状态可以简化为三种：Leader、Follower 和 Candidate。在任何时刻，每一个服务器节点都只可能出于这三种状态之一。

- Leader：领导者，负责处理客户端请求和日志复制。
- Follower：跟随者，接收领导者的指令并执行日志复制
- Candidate：候选者，当跟随者没有收到领导者的心跳信号时，它会变为候选者，发起领导者选举。

Raft 把时间划分为任意长度的任期（Term），每个任期都有一个唯一的编号。任期编号是单调递增的，随着时间的推移，任期编号会不断增加。

每一段任期从一次选举开始。在某些情况下，一次选举无法选出leader(比如两个节点收到了相同的票数)，在这种情况下，这一任期会以没有leader结束；一个新的任期(包含一次新的选举)会很快重新开始。Raft 可以保证在任意一个任期内，最多只有一个leader。

任期的机制可以非常明确地标识集群的状态，并且通过比较任期，我们可以快速查询一台服务器的历史状态：比如，通过查看一台服务器是否具有2任期的日志，我们可以判断它在2任期是否发生过宕机。

Raft算法中服务器节点之间使用RPC进行通信，并且Raft中只有两种主要的RPC: ---什么是rpc

- RequestVote RPC(请求投票)：由candidate在选举期间发起。

- AppendEntries RPC(追加条目)：由leader发起，用来复制日志和提供一种心跳机制。

> 服务器之间通信的时候会交换当前任期号；如果一个服务器上的当前任期号比其他的小，该服务器会将自己的任期号更新为较大的那个值。

> 如果一个candidate或者leader发现自己的任期号过期了，它会立即回到follower状态。

> 如果一个节点接收到一个包含过期的任期号的请求，它会直接拒绝这个请求。

# 领导者选举

Raft内部有一种心跳机制，如果存在leader，那么它就会周期性地向所有follower发送心跳，来维持自己的地位。

在我的理解中，所谓心跳

如果follower一段时间没有收到心跳，那么他就会认为系统中没有可用的leader了，然后开始进行选举。

开始一个选举过程后，follower会以以下步骤进行选举，试图成为leader。这些步骤的顺序非常重要：
1. follower先增加自己的当前任期号，并转换到candidate状态。
2. 然后投票给自己，并且并行地向集群中的其他服务器节点发送投票请求(RequestVote RPC)

对于一个 candidate 来说，投票选举阶段最终可能产生三种结果：成功，失败，未决出胜负。
- 成功：它得到了 **超过半数** 的投票，赢得选举，成为新的leader。
- 失败：它没有得到 **超过半数** 的选票，或者它直接收到了已经成功的新 leader 的心跳。此时，它将执行 **状态简化** 中提到的几个步骤 最终更新自己的任期 并成为一个follower。
- 未果：有多个follower同时成为candidate，因此场上没有任何一个节点得到 **超过半数** 的选票，candidate 们将在 **随机选举超时时间** 后增加任期号 并开启新一轮选票。

> 论文中给出的随机选举超时时间为 150ms ~ 300ms


论文中，关于这两个RPC的详细定义和参数说明大致如下：

```go
// 请求投票 RPC arguments 是candidate发给follower的请求
type RequestVoteArgs struct {
    Term         int // 候选人的任期号
    CandidateId  int // 候选人的 ID
    LastLogIndex int // 候选人最后日志条目的索引值
    LastLogTerm  int // 候选人最后日志条目的任期号
}
```

```go
// 请求投票 RPC results 是follower发给candidate的响应
type RequestVoteReply struct {
    Term        int  // 当前任期号，以便于候选人去更新自己的
    VoteGranted bool // 候选人赢得了此张选票时为真
}
```
对于没有成为candidate的follower节点，对于**同一个任期**，会按照先来先得的原则投出自己的选票。

# 日志复制

Leader被选举出来后，开始为客户端请求提供服务。

客户端怎么知道新leader是哪个节点呢?



Leader接收到客户端的指令后，会把指令作为一个新的条目追加到日志中去。

一条日志中需要具有三个信息:

- 状态机指令本身
- leader的任期号 Term
- 日志号(日志索引) idx

Leader 将并行发送 AppendEntries RPC给 follower，让它们复制该条目。

当该条目被超过半数的follower复制后，leader就可以在本地执行该指令并把结果返回客户端。

我们把本地执行指令，也就是leader应用日志与状态机这一步，称作提交。
